# 6. 演示演练、实操复现与团队工程落地实践

[指南目录](../README.md) · [English](../en/06-workshop.md) ·
[上一章：工程判断](05-engineering-judgment.md) · [证据索引](../evidence.md)

具体的演示实操路线已在配套的演示仓库中结构化归档。本章详细说明如何根据团队诉求规划三类工程实践路径：零模型调用的离线纯本地练习、从零复现完整的端到端受控交付，以及专项工程实验。团队可根据时间预算、权限环境与算力成本灵活选择，无需强求一次性全部走完。

## 6.1 实践路径选型：研读归档还是从零运行？

| 实践选型 | 核心演练动作 | 结论陈述与归档边界 |
|---|---|---|
| **观摩已归档案例** | 通读方法指南、审计截图与历史流转记录 | 客观转述案例在当时演练中记录的历史实测指标 |
| **本地离线验证** | 在隔离资源中拉起已审查的生产镜像，或执行离线测试 | 严格陈述自己在本地环境中亲身验证过的系统行为 |
| **从零端到端演练** | 建立独立的远程仓库，配置权限凭证，调用大模型并完成全周期验证 | 详尽记录本次演练全过程，包含偶发摩擦、重试轮次与人工介入事实 |

若仅需面向团队或客户进行宣讲展示，无需额外搭建内部文档站点。可直接打开
[公共 Trace Viewer 在线查看器](https://huangyingting.github.io/ai-native-sdlc/)，交互式复盘大模型调用拓扑。
如需现场操作体验服务台应用，建议提前在本地通过隔离 Docker 容器拉起；报告和截图中出现的 localhost 地址仅为历史演练留痕，非公网在线演示地址。截图与运行记录的溯源索引请参阅[证据索引](../evidence.md)。

## 6.2 演示路线复用指南

[30 分钟标准演示路线](https://github.com/huangyingting/ai-native-sdlc-demo/blob/main/docs/presenter.md)
严格按照业务逻辑推进：工单流转界面切入 → 4 项核心业务决策 → Spec/Plan 双重审批 → 两轮测试用例审查修订 → 38 项全量测试绿灯 → 镜像发布权限修复恢复 → 基于确切镜像完成现场业务验收。
该路线基于演示仓库中归档的真实数据与 14 张高清过程截图，切勿与其它演练中的测试数据混淆。

在演示前建议提前在浏览器中打开对应页面。只读讲解无需在 Issue 中发表评论、提交审批指令或触发重跑流水线。若演练时间充裕可扩展至 1 小时，可适度穿插第 5 章的工程评测方法论；半天或全天工作坊可组织下文所述的动手实操。需要注意的是：由于完整的云端交付受排队延迟、人工评审、鉴权以及容器构建耗时影响，不建议承诺在固定的紧凑时段内现场从零跑完完整流程。

### 标准的页面审查动线

- **GitHub Issue**：原始业务痛点 → 主讨论区（Hub）→ 渲染后的完整文档版本 → 架构决策指令 → 人工审批指令。
- **GitHub PR**：目标合并分支与当前提交 SHA → 改动文件 Diff → 同行评审意见 → 自动化 Checks 状态 → 合并入库。
- **GitHub Actions**：源码关联 Commit → 流水线运行编号（run）与轮次（attempt） → 必需门禁状态 → 详细日志与度量摘要。
- **业务应用 UI**：准备基准测试数据 → 模拟一线人员操作 → 核对流转结果 → 验证多维筛选与数据落盘。
- **Trace Viewer**：总览模型运行信息 → 调用时序拓扑 → 验证并发重叠窗口 → 偶发错误自愈 → 真实 Token 开销。

## 6.3 路径 A：零模型调用的纯本地离线演练

在源仓库根目录下，使用 Node.js 24 执行：

```sh
npm test
npm --prefix demos/engineering-lab test
node tools/brownfield-demo/cli.mjs --help
node tools/brownfield-demo/cli.mjs scenario list
node tools/engineering-demo/cli.mjs --help
```

上述单元测试与帮助指令不会发起任何外部 Copilot API 调用。若提示依赖缺失，请遵循所属模块的说明补充安装，切勿将演示应用的依赖混入仓库根目录。

本工程在初始基线下，全量测试包含 456 项仓库级自动化测试与 15 项实验应用测试。测试用例总数可能随工程演进而动态调整，演练时应如实记录本地实测结果。`scenario list` 展示的是标准化场景定义，状态标记为 `planned-not-evidence`，切不可将其当成已执行完毕的审计凭证。

无需调用大模型即可开展的离线研讨题目：

1. 对照主线案例中的 Intent 与已获批的 Spec，精准找出一项决策所对应的验收断言，以及一项明确划定的非目标（Out of Scope）。
2. 研读 Tests PR 审查记录，尝试构思一段能够“侥幸骗过弱断言”的错误实现代码。
3. 对比运维维护中失败的实现与生成的后续任务，阐述系统修复了什么、如实保留了哪些审计失败。
4. 深入剖析在工程实验评测中，为什么系统最终返回状态既不是“全部崩溃”，也不是“全部验收通过”。

## 6.4 路径 B：从零开启一轮完整的受控交付

具体操作步骤请严格参考[分步演练指南](../../brownfield-human-gated-delivery-walkthrough.md#1-prepare-the-repository)。准备工作应遵循严格的时序：

1. 选定并审查一个**完整的 40 位源提交 SHA**。该基线版本必须包含必要的工作流脚本，但尚未实现工单责任人特性；坚决不能使用已完成交付的演示仓库作为演练起点。
2. 确定源码树外部的目标空目录、获准创建的独立远程仓库以及审批策略模式。目标目录必须尚不存在，且其父目录必须真实存在。
3. 执行标准化场景导出：

   ```sh
   node tools/brownfield-demo/cli.mjs prepare \
     --source /absolute/path/to/ai-native-sdlc \
     --source-ref FULL_40_HEX_COMMIT \
     --dest /absolute/path/to/new-isolated-demo \
     --reviewer YOUR_GITHUB_LOGIN \
     --scenario ownership-standard
   ```

4. 核对导出内容与溯源记录（Provenance），确认无敏感数据外泄。`prepare` 指令仅负责本地生成文件，绝不擅自执行 Git 初始化、创建远程仓库或推送代码。
5. 初始化本地 Git 并发布至经审批的远程仓库，确认远程 `main` 分支合规就绪、工作流顺利注册且审查者权限正确生效。
6. **在全新导出的目标仓库中**，核查 Copilot 订阅配额、GHCR 镜像读写授权以及预设的分支保护规则。按安全合规规程在 Actions 中注入 `COPILOT_ASSIGN_TOKEN`。
7. 运行只读前置预检（Preflight），由法定审查者复核无误。
8. 正式提交本次业务需求 Intent，遵循第 2 至第 4 章的方法论推进全流程开发与最终验收。

只有在明确开展单人自主演练时，方可启用 `--single-owner` 选项，并在 prepare、setup 与 preflight 各阶段保持配置口径一致。单人模式仅用于演示体验，不代表生产级的多人独立审查。源仓库的 `main` 主干特意未施加完整分支保护，严禁误在源仓库根目录下直接执行全套初始化。访问令牌严禁硬编码至命令或聊天沟通中，亦严禁通过 `git push --force` 强行覆盖历史交付成果。

**若遇到以下阻断情况，必须立即暂停流程排查**：权限或费用未确认、工作流未正确注册、代码基线 Hash 漂移、审查者权限失配、必需门禁失败、镜像冒烟异常或临时沙箱清理失败。只有彻底排除阻断因素后，方可继续推进。

## 6.5 路径 C：针对特定架构课题的专项实验

### 变更影响分析与 Agent 策略评测

演练环境要求就绪：Node.js 24、Docker、Git 以及已完成授权登录的 Copilot CLI，并确认已具备足够的模型配额。在开始前请先核验[经测试验证的 CLI 版本与通信协议](../../engineering-judgment-demos.md#2-prerequisites)；单纯版本号更新并不保证协议兼容。

已发布评测基准所绑定的应用基线为 `540cacd2a10be5ed326479fd959d21eec5d4997c`。应用基线 Hash 与评测工具版本必须分别独立归档。每次运行均必须使用专属的输出目录，同一组对比实验必须使用完全相同且不可变的运行镜像。

遵循 [impact 演练规程](../../engineering-judgment-demos.md#3-change-impact-and-consistency-loop)依次执行：

1. `impact-propose`：调用模型生成变更影响方案，随后人工通读全文。
2. `impact-approve`：审查无误后，针对指定的 `proposalHash` 生成本地审批凭据。该指令退出码为 0 仅代表凭据文件生成成功，绝不代表该方案可以直接免审放行。
3. `impact-implement`：次轮受限调用，要求模型基于获批方案生成代码，并在隔离沙箱中执行既有测试与独立判定器（Oracle）检查。
4. 可选基准压测 `benchmark`：运行 6 个标准化实验单元，计划共发起 9 次真实模型调用。

上述实验完全由 CLI 驱动，不提供 Web UI 交互，亦不自动提交 PR。运行后必须完整归档方案文本、审批凭据、Token 用量、候选补丁、测试与判定器报告、环境版本信息以及全部失败日志。提案生成阶段退出码为 0 仅代表**正在等待人工架构审查**；退出码 2 代表实验跑通但存在用例未通过关卡；退出码 1 代表发生执行异常。

### 零模型调用的可靠性工程演练

在确认代码已实现就绪探测（Readiness）且具备镜像拉取权限的前提下，首先执行[测试有效性验证](../../brownfield-reliability-loops.md#3-start-here-qualify-the-tests)，随后执行[端到端运行演练](../../brownfield-reliability-loops.md#4-run-real-image-verification-admission-recovery-and-monitoring)。
上述演练会执行本地测试、Docker 容器调度、HTTP 探测与 SQLite 数据审计，全程不发起任何 Copilot 模型调用。但镜像拉取与计算资源消耗仍可能产生基础算力费用。

在启动前请务必确认应用基线已正确引入就绪接口，并使用专属的测试数据卷与隔离资源。坚决禁止向共享的开发或生产环境中直接注入故障。演练生成的维护复盘草案依然必须经过人类审查与工程落地，绝不能直接算作长效预防性措施已经完成。

## 6.6 交付意外中断的恢复策略与归档留痕

| 异常中断场景 | 标准化处置方案 |
|---|---|
| **文档生成或阶段交接中断** | 排查网络或令牌鉴权故障后，在 Issue 中提交 `/sdlc retry`，或手动重新触发 Documents 工作流 |
| **工程 CI / Advance / Publish 任务失败** | 修复触发失败的根因代码后，在 GitHub Actions 界面重新运行失败的任务（文档 retry 指令不处理代码 CI） |
| **需要临时暂停正在运行的交付流转** | 在 Issue 中提交 `/sdlc pause`，排障完毕后提交 `/sdlc resume`，严禁直接在数据库或分支中强改状态 |
| **已冻结的规格发现重大逻辑遗漏** | 另立专门的 Intent 或维护任务，详细说明取消原因，完好保留此前已封存的历史审计记录 |
| **工作流产物或日志已过保存期限** | 查阅仓库中永久持久化归档的 JSON 审计报告与 Commit 记录；在复盘中清晰注明哪些临时证据已不可溯源 |
| **本地演示环境临时无法连通** | 借助注明日期的留痕截图进行演讲阐述，或在全新的隔离端口上重新拉起容器镜像复测 |

每次运行至少保留：

```text
仓库 + Intent URL + 执行模式
源代码与工具提交 + 场景与输入哈希
决策 + Spec／Plan 版本和哈希 + 批准人
测试与实现提交 + Red／Green run 和 attempt
合并 SHA + 镜像 digest + 验证 run 和 attempt
验收操作与观察 + 未验证项
失败／重试／人工介入 + 实际用量
资源归属 + 清理结果 + 后续维护任务
```

私有提示词、原始 CLI 事件、数据库、请求数据和日志不要提交到 Git。
自动脱敏无法保证所有自由文本都不含敏感信息；公开前仍应审查，只发布合适的摘要和引用。

## 6.7 先落地一个可信闭环，再扩大规模

| 步骤 | 团队约定 | 可观察结果 |
|---|---|---|
| 1. 选择一项实际的小变更 | 负责人、范围、基线和不做的事 | 经审查的 Intent |
| 2. 澄清歧义 | 谁做决定，哪些问题不解决就不能推进 | 决策记录和可测试的验收标准 |
| 3. 分开规定提案与批准权限 | 可用工具、可改文件，以及审查和执行角色 | AI 无法自行批准或扩大修改范围 |
| 4. 独立验证 | 已有功能、异常场景及对应版本 | 可重复执行的检查 |
| 5. 验收指定镜像 | 部署与恢复负责人、验收步骤 | 对应镜像 digest 的操作记录 |
| 6. 持续观察与测量 | 如何收集运行反馈，如何衡量质量和成本 | 经审查的后续任务和可比较的数据 |

可关注首轮验收通过率、上线后才发现的回归缺陷、审查中发现的无依据假设、
返工次数、交付耗时、人工介入和模型用量。先建立基线，再按一致规则测量。
本仓库尚未提供经过测量的客户投资回报（ROI）。

按仓库规则声明 **Demo Ready** 之前，需要分别完成三次由人实际参与决策的独立
隔离演练：正常交付、主动修订 Spec 并使 Plan 失效、从可恢复失败中继续执行。
当前已验收案例不等于这三个场景全部完成；脚本化开发测试也不能替代这些要求。

采用 AI 的目的，不是取消所有检查，而是：
**更快地提出有用方案，更清楚地作出决定，并让交付结果经得起验证。**
