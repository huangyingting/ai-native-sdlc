# 6. 演示、实操与团队落地

[指南目录](../README.md) · [English](../en/06-workshop.md) ·
[上一章](05-engineering-judgment.md) · [证据索引](../evidence.md)

具体演示路线在演示仓库维护。本章说明如何准备和开展三种实践：
不调用模型的本地练习、从头完成一次交付，以及专题实验。
可以根据时间、权限和预算选择，不必一次做完。

## 6.1 先决定：看案例，还是亲自运行？

| 方式 | 做什么 | 如何描述结果 |
|---|---|---|
| 查看案例 | 阅读指南、截图和演练记录 | 说明案例当时的结果 |
| 本地验证 | 在隔离资源中启动已审查的镜像，或执行离线检查 | 报告自己实际验证的行为 |
| 从头演练 | 准备独立仓库或输出目录，配置权限，调用模型并完成验证 | 记录本次全过程，包括失败、重试和人工介入 |

只做讲解时，无需部署文档网站。还可以打开
[公共 Trace Viewer](https://huangyingting.github.io/ai-native-sdlc/)，交互查看调用过程。
若要现场操作应用，需要自行启动隔离实例；报告中的 localhost 地址不是公共演示地址。
截图和运行记录的来源说明见[证据索引](../evidence.md)。

## 6.2 使用演示仓库中的讲解路线

[30 分钟演示路线](https://github.com/huangyingting/ai-native-sdlc-demo/blob/main/docs/presenter.md)
依次展示交接界面、四项产品决定、Spec／Plan 批准、两轮测试修改、
38 项测试通过、发布权限恢复，以及确切镜像的验收。
它使用当前仓库的实际记录和 14 张截图，不再混用其他案例的人员名单或测试数量。

演示前先打开需要的页面。只读讲解不需要发评论、执行批准或重跑工作流。
需要扩展到一小时，可加入第 5 章的工程判断方法，但不要将实验设计讲成已完成的交付。
半天工作坊可加入下文练习；完整云端交付受排队、审查、权限和构建耗时影响，
不宜承诺在固定时段内完成。

### 页面阅读顺序

- **Issue：** 原始需求 → 当前汇总区（hub）→ 完整文档版本 → 决策 → 批准。
- **PR：** 目标分支与当前提交 → 文件变更 → 审查 → 检查 → 合并。
- **Actions：** 源代码版本 → run／attempt → 必需任务 → 日志与摘要 →
  经审查的工作流产物；需要登录时，使用有权限的账号访问。
- **应用：** 准备固定数据 → 执行用户操作 → 检查结果 → 检查持久化和异常输入。
- **Trace：** 运行信息 → 调用关系 → 执行时间是否重叠 → 错误 → 实测用量 → 未验证项。

## 6.3 路线 A：不调用模型的本地练习

在源仓库根目录，使用 Node.js 24：

```sh
npm test
npm --prefix demos/engineering-lab test
node tools/brownfield-demo/cli.mjs --help
node tools/brownfield-demo/cli.mjs scenario list
node tools/engineering-demo/cli.mjs --help
```

这些测试和帮助命令不会调用 Copilot。若缺少依赖，请按所属项目的说明安装或恢复，
不要将演示应用的依赖加到仓库根目录。

工程专题发布时，验证结果为 456 项仓库测试和 15 项实验应用测试。
测试数量会随代码版本变化，练习时应记录自己的运行结果。
`scenario list` 展示的是场景定义，状态为 `planned-not-evidence`，
不能将其当作执行完成的记录。

不调用模型也能进行的练习：

1. 对照案例的 Intent 和已批准 Spec，找到一条决策对应的验收条件，以及一个非目标。
2. 阅读 Tests 审查，设计一个能骗过薄弱断言的错误实现。
3. 对比失败的维护实现与后续任务，说明修正了什么、保留了哪些记录。
4. 解释工程实验为什么既不是“全部失败”，也不是“全部验收成功”。

## 6.4 路线 B：从头完成一次交付

具体操作以[分步操作手册](../../brownfield-human-gated-delivery-walkthrough.md#1-prepare-the-repository)
为准。准备工作按以下顺序进行：

1. 选定并审查一个**完整的 40 位源提交 SHA**。该版本应包含所需工作流，
   但尚未实现工单归属；不要使用当前已验收的演示应用作为起点。
2. 确定源码目录之外的目标目录、获准创建的独立远程仓库，以及审查模式。
   目标目录必须尚不存在，但其父目录必须已存在。
3. 导出指定场景：

   ```sh
   node tools/brownfield-demo/cli.mjs prepare \
     --source /absolute/path/to/ai-native-sdlc \
     --source-ref FULL_40_HEX_COMMIT \
     --dest /absolute/path/to/new-isolated-demo \
     --reviewer YOUR_GITHUB_LOGIN \
     --scenario ownership-standard
   ```

4. 检查导出内容和来源记录（provenance），确认适合公开。`prepare` 不会初始化 Git、
   创建远程仓库或推送内容。
5. 初始化并发布审查过的导出内容，确认远程 `main`、工作流注册情况和审查者权限。
6. **在导出的仓库中**预览设置，确认权限、Copilot 使用资格、镜像访问和拟配置的
   分支保护。只应用已同意的改动，并按安全流程配置凭据。
7. 执行只读预检（preflight），请有权限的审查者确认。
8. 提交本次 Intent，按第 2–4 章完成开发和验收。

只有明确选择单人演练时才使用 `--single-owner`，并在 prepare、setup 和 preflight
中保持设置一致。单人演练不等于独立审查。源仓库的 `main` 特意未设置完整保护，
不要误在源仓库执行全套 setup。访问令牌不要写进命令或聊天，也不要用强制推送
覆盖已经交付的仓库状态。

**遇到以下情况应暂停：** 权限或费用未确认、工作流未注册、基线不匹配、
没有可用的审查者、必需检查失败、镜像尚未验证，或资源清理失败。
先解决问题，再继续流程。

## 6.5 路线 C：围绕一个问题做专题实验

### 变更影响与策略评估

准备 Node.js 24、Docker、Git 和已登录的 Copilot CLI，并确认可以承担调用费用。
先核对[已验证的 CLI 版本和协议](../../engineering-judgment-demos.md#2-prerequisites)；
版本号更高并不保证兼容。

已发布实验所用的应用基线为 `540cacd2a10be5ed326479fd959d21eec5d4997c`。
应用基线与执行工具的版本应分别记录。每次使用独立的输出目录，
同一组对比实验使用相同且固定的运行镜像。

按照 [impact 操作步骤](../../engineering-judgment-demos.md#3-change-impact-and-consistency-loop)执行：

1. `impact-propose`：调用模型生成方案，随后阅读完整内容。
2. `impact-approve`：审查后，针对指定 `proposalHash` 生成本地批准凭据。
   生成命令退出码为零，并不意味着方案可以直接批准。
3. `impact-implement`：第二次调用模型生成实现，在受限环境中执行测试和 oracle 检查。
4. 可选的 `benchmark`：运行六个实验单元，按计划共调用模型九次。

这些实验通过命令行操作，没有独立 Web 界面，也不会自动完成 GitHub 交付。
完整语法可通过上文的 `--help` 查看。运行后保留方案、批准记录、用量、
候选实现、测试与 oracle 结果、源代码和工具版本，以及全部失败记录。
提案阶段的退出码 0 可能仅表示**正在等待操作者审查**；退出码 2 表示实验已完成，
但有候选未通过验收；退出码 1 表示执行错误。

### 无需调用模型的可靠性实验

准备好已实现 readiness 的源代码，并确认镜像访问权限后，先执行
[测试有效性验证](../../brownfield-reliability-loops.md#3-start-here-qualify-the-tests)，
再执行[运行演练](../../brownfield-reliability-loops.md#4-run-real-image-verification-admission-recovery-and-monitoring)。
这些步骤会运行测试、Docker、HTTP 请求和 SQLite 检查，但不调用 Copilot。
镜像与依赖下载、计算资源仍可能产生费用。

开始前确认应用确实已实现 readiness，并使用单独的数据卷和实验资源。
不要对共享工作负载注入故障。生成的维护草稿也仍需审查和实施，不能直接算作
预防措施已经完成。

## 6.6 中断后怎样继续，结束后留下什么？

| 情况 | 处理方式 |
|---|---|
| 文档生成或交接失败 | 排查原因后，按文档使用 `/sdlc retry`，或为同一 Intent 触发 Documents 工作流 |
| 工程 CI／Advance／Publish 失败 | 修正原因后，重跑失败的 Action；文档重试命令不处理这些任务 |
| 需要暂停活动运行 | 使用 `/sdlc pause`，之后 `/sdlc resume`，不直接改状态 |
| 冻结范围有误 | 另建 Intent 或后续任务，保留取消原因和记录 |
| 工作流产物过期 | 查阅持久保存的报告、提交和 Issue；明确标注哪些原始证据已无法访问 |
| 本地应用不可用 | 使用注明日期的截图讲解，或自行启动隔离实例后验证 |

每次运行至少保留：

```text
仓库 + Intent URL + 执行模式
源代码与工具提交 + 场景与输入哈希
决策 + Spec／Plan 版本和哈希 + 批准人
测试与实现提交 + Red／Green run 和 attempt
合并 SHA + 镜像 digest + 验证 run 和 attempt
验收操作与观察 + 未验证项
失败／重试／人工介入 + 实际用量
资源归属 + 清理结果 + 后续维护任务
```

私有提示词、原始 CLI 事件、数据库、请求数据和日志不要提交到 Git。
自动脱敏无法保证所有自由文本都不含敏感信息；公开前仍应审查，只发布合适的摘要和引用。

## 6.7 先落地一个可信闭环，再扩大规模

| 步骤 | 团队约定 | 可观察结果 |
|---|---|---|
| 1. 选择一项实际的小变更 | 负责人、范围、基线和不做的事 | 经审查的 Intent |
| 2. 澄清歧义 | 谁做决定，哪些问题不解决就不能推进 | 决策记录和可测试的验收标准 |
| 3. 分开规定提案与批准权限 | 可用工具、可改文件，以及审查和执行角色 | AI 无法自行批准或扩大修改范围 |
| 4. 独立验证 | 已有功能、异常场景及对应版本 | 可重复执行的检查 |
| 5. 验收指定镜像 | 部署与恢复负责人、验收步骤 | 对应镜像 digest 的操作记录 |
| 6. 持续观察与测量 | 如何收集运行反馈，如何衡量质量和成本 | 经审查的后续任务和可比较的数据 |

可关注首轮验收通过率、上线后才发现的回归缺陷、审查中发现的无依据假设、
返工次数、交付耗时、人工介入和模型用量。先建立基线，再按一致规则测量。
本仓库尚未提供经过测量的客户投资回报（ROI）。

按仓库规则声明 **Demo Ready** 之前，需要分别完成三次由人实际参与决策的独立
隔离演练：正常交付、主动修订 Spec 并使 Plan 失效、从可恢复失败中继续执行。
当前已验收案例不等于这三个场景全部完成；脚本化开发测试也不能替代这些要求。

采用 AI 的目的，不是取消所有检查，而是：
**更快地提出有用方案，更清楚地作出决定，并让交付结果经得起验证。**
