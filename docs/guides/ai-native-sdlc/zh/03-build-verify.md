# 3. 开发与验证：先审查测试断言，再检验功能实现

[上一章：需求、规格与计划](02-intent-spec-plan.md) · [下一章：部署、运行与维护](04-deploy-operate.md)

本章继续以 **“工单负责人”真实交付案例** 为核心，系统阐述现代 AI 原生工程中的测试与验证方法论：测试断言如何才能构成对代码实现的刚性约束？当测试套件本身存在逻辑偏差时，技术团队又该如何严谨处置？

## 3.1 严格解耦“测试编写”与“功能实现”阶段

在实施计划（Plan）获得正式批准后，自动化流水线将以已批准的文档提交为基线拉出独立的工程分支。系统首先**仅下发测试用例编写任务（Tests）**，坚决不提前分配业务实现任务。测试 PR 合并至本次交付的生命周期分支；随后创建的实现 PR（Implementation PR）才承载完整的生产代码改动，最终目标合并分支为主干 `main`。

[![测试审查指出被预期失败遮住的断言问题](https://raw.githubusercontent.com/huangyingting/ai-native-sdlc-demo/main/docs/cases/assets/ownership/tests-request-changes.png)](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8#pullrequestreview-5486915007)

**测试审查实录**：[huangyingting/ai-native-sdlc-demo#8](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8)（记录于 2026 年 10 月 12 日）。审查人员首先核验目标分支、所属交付阶段与改动文件范围，随后深入检视 **Files changed**、**Checks** 及[第二轮修改要求（Request Changes）](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8#pullrequestreview-5486915007)。

| Tests 阶段允许的工程行为 | Tests 阶段坚决禁止的越界行为 |
|---|---|
| 编写具备明确业务约束力的验收断言 | 提前偷跑或混入生产功能的实现代码 |
| 运行测试套件并精准登记预期失败清单 | 未在真实环境中执行测试便主观臆造失败清单 |
| 在测试批准前持续修正逻辑薄弱的用例 | 为迁就测试编写而擅自倒逼修改已冻结的 Spec/Plan |
| 严格保留既有存量功能的全部回归测试 | 将语法报错、跳过用例（skip）或测试钩子异常充当有效 Red |

## 3.2 理解受控红灯（Controlled Red）：测试是红的，门禁却必须是绿的

受控红灯（Controlled Red）绝非“只要测试运行报错就行”。本体系所定义的严密受控红灯，必须同时满足以下 4 项硬性条件：

1. **存量基线完全绿灯**：未作修改的既有回归测试全部 100% 通过。
2. **测试路径有效触达**：新增的功能测试确实执行到了预期位置，而非在前置准备阶段被动崩溃。
3. **失败原因精准归因**：测试用例失败的唯一原因系待测生产特性尚未实现，且失败的测试用例名称与范围必须与登记的清单精确一致。
4. **编译与代码质量健康**：代码编译、TypeScript 类型检查、ESLint 与构建均正常，未夹杂任何无关报错。

流水线中的 `tdd-red` 检查项校验的正是上述 4 项受控指标。因此，**业务测试用例应当按预期报错（Red），而流水线阶段校验任务（`stage-validation`）则必须全绿通过（Green）**。这两者检验的是完全不同的工程维度：前者验证业务功能的缺失状态，后者验证本次测试失败是否完全符合生命周期的受控规范。技术人员绝不能以“反正是红灯”为借口，盲目忽视阶段校验门禁的报警。

在本次交付的[最终受控 Red 复核中](https://github.com/huangyingting/ai-native-sdlc-demo/actions/runs/38210170335/attempts/2)，
流水线首先核验既有 26 项回归测试全部通过，随后校验测试提交中的 38 项完整测试集：**29 项正常通过，9 项为精确匹配的业务预期断言失败**，未包含任何跳过用例或基础设施异常。最终获批的测试提交为 `104be0889c54652bec8f9bc317ffa5f0cf33166f`。

## 3.3 审视断言有效性：穿透“表面覆盖率”的伪装

在工单负责人案例中，AI 最初生成的测试套件并未直接获批。根本原因在于：测试在形式上覆盖了功能路径，绝不代表它具备甄别错误代码的实质能力：

| 表面看似覆盖的弱指标（防踩坑） | 真正具备约束力的强断言 |
|---|---|
| 下拉组件的选项里包含候选成员名字 | 在目标工单行、详情页元数据中真实渲染出责任人文本 |
| 表单提交后时间戳表面看起来未变 | 借助独立 SQLite 连接核验 `PRAGMA data_version`，确认底层未发生任何冗余写入 |
| 服务端更新接口返回 200 成功响应 | 分配、转交或清空负责人后，在关闭并重开数据库后依然能完整持久化还原 |
| 某个搜索查询能够返回全部记录 | 针对组合条件筛选，断言其多维交集的精准集合与空集占位表现 |
| HTML 模板中存在 selected 属性 | 真实挂载交互组件并模拟路由跳转，断言导航后控件状态能够自动双向同步 |
| 某个字段能够被成功更新 | 严格断言仅有白名单内的字段发生变动，其余无关字段与数据行绝无副作用 |

在审查测试用例时，审查者应当反复叩问自己：**假若开发人员写出了一段完全错误的代码，当前这个断言有没有可能依然侥幸通过？**
如果答案是“有可能”，就必须立即强化断言逻辑，或在文档中清晰注明其未覆盖的风险盲区。片面堆砌无意义的测试用例数量，对提高软件质量毫无实质助益。

本次交付的测试审查经历了 2 轮修改：第 1 轮排除了名称层级不符、历史数据样本失真与断言浅层化缺陷；而在第 2 轮中，即使 CI 门禁已判定受控 Red 通过，审查人员深入检视时依然捕获了筛选断言逻辑矛盾、时间戳预期自相冲突、DOM 查找跨层越界，以及未推进模拟时钟导致重复保存断言形同虚设等深层缺陷。之所以 CI 会放行，是因为这些错误断言位于更早的前置失败断言之后，尚未被运行到。**自动化 CI 绿灯与测试逻辑本身的严谨性，是两码事。**

## 3.4 功能实现必须直面已冻结测试的刚性检验

当 Tests PR 经审查合并后，AI 方可正式下发实现代码。在此阶段，代码审查的核心关注点包括：

- 数据库表结构迁移、参数校验与核心业务逻辑是否严密兑现了 Spec。
- 前端交互与后端 API 是否真正联通，是否存在编写了辅助函数却从未被实际调用的“假代码”。
- 已获批的测试用例、规格文档与失败清单是否保持逐字节一致（未受任何篡改）。
- 若确需追加边界回归测试，是否在独立的测试文件中扩展，而非擅自修改已冻结的文件。
- 门禁校验与人工批准是否严格绑定至当前 PR 最新的提交（Head Commit），而非历史提交。

由 Coding Agent 提交的[工单负责人实现 PR](https://github.com/huangyingting/ai-native-sdlc-demo/pull/9)
全量通过了 Stage Green 与应用级完整 CI 检查，包括 **38 项全量测试绿灯、ESLint 检查、生产构建与 Docker 容器端到端冒烟测试**。先前的 9 项受控 Red 断言全量转绿，9 个已冻结的契约与测试文件保持未修改。

| 核心必检门禁 | 关键核查内容 |
|---|---|
| `stage-validation` | 校验已冻结契约文件未受任何篡改，此前处于受控 Red 的全部业务断言转为全绿通过 |
| `validate` | 应用级完整单元测试、TypeScript 类型检查、ESLint 静态检查与生产打包构建 |
| `container-smoke` | 拉起基于生产环境构建的 Docker 容器并成功执行前端冒烟检查 |
| 交付策略策略门禁 (Delivery policy) | 当前版本已获得法定授权审查者的显式批准，严格满足分支保护与质量规则 |

在提交任何追加修改后，流程必须按规则重新触发审查。需要强调的是：负责任务调度的 GitHub Actions 工作流运行成功，绝不代表其所调度的下游应用检查全部通过，必须深入检视具体的任务输出。

## 3.5 测试自身存在缺陷时，坚决禁止通过修改业务代码来迁就

红灯（Red）仅能证明当前测试抛出了失败，无法保证后续断言及测试治具本身毫无缺陷。在日常工程排错中，技术人员必须具备高度的专业敏锐度，准确区分**业务代码缺陷**、**测试套件缺陷**与**环境配置异常**。

当需要验证测试治具自身的有效性时，应在隔离环境中进行独立测试，详实记录输入上下文与实测指标，坚决不能将其包装成阶段性的功能绿灯。一旦发现已冻结的测试套件中存在逻辑错误，必须另行创建维护任务明确更正范围并重新发起审查，坚决杜绝通过扭曲业务实现代码来迁就错误的测试断言，亦严禁私自篡改已归档的冻结文件。

## 3.6 变异测试实践：故意注入故障，检验测试的“捕虫能力”

除验证实现代码能否使测试转绿外，还应主动验证测试套件是否具备识别异常实现的敏感度。例如，针对就绪健康检查契约，可在隔离环境中逐一注入下列代码变异（Mutations），检验测试套件能否精准报警：

| 主动注入的代码变异 | 为什么测试断言必须能够精准报错 |
|---|---|
| 省略底层真实的数据库读取逻辑 | 表面看似健康的探测接口，实际上可能根本未连通真实存储依赖 |
| 数据库探测抛错时仍返回 200 状态码 | 严重故障的后端实例会被网关误判为就绪，进而被盲目分发流量导致雪崩 |
| 探测成功或失败时均未输出 `Cache-Control: no-store` | 浏览器或中间代理缓存了先前的探测状态，严重掩盖了系统当下的真实可用性 |
| 在诊断日志中直接输出原生 Error 堆栈 | 未脱敏的异常堆栈极易在日志系统中暴露敏感的基础设施连接串与内部拓扑 |
| 随意修改已捕获的冻结异常对象 | 错误处理代码本身发生逻辑二次报错，导致服务进程非预期退出 |

严密的变异测试执行时序应当为：原始代码全绿跑通 → 逐一注入变异代码并断言测试精准变红 → 还原实现后测试再次全绿。在此过程中，测试套件代码保持未修改，并提前界定合法的断言失败类型。若因代码语法错误、导入缺失或超时导致崩溃，绝不能算作测试套件精准捕获了业务缺陷。

所得出的技术结论应严格限定在实际验证过的变异案例范围内，杜绝随意吹嘘全工程的变异测试得分。具体操作请参阅[可靠性演练指南](../../brownfield-reliability-loops.md)。

## 3.7 常见故障归因与标准化应对策略

| 实测观察现象 | 标准化处置规程 |
|---|---|
| 尚未执行到核心业务断言，测试在前置依赖或模块导入阶段即崩溃 | 修复测试运行环境或治具配置；该报错属于环境异常，绝不计为有效受控 Red |
| 代码实现明显违背了已批准的 Spec 约定 | 在既定契约约束内针对性修改生产代码，重新触发全量检查 |
| 在测试套件获批前，审查发现断言深度或边界覆盖不足 | 完善测试断言，重新提交并执行受控 Red 门禁核验 |
| 已冻结的契约规范或测试治具被证实存在逻辑设计缺陷 | 另立专门 Issue 说明修订范围，留存历史失败记录后重新走评审流转 |
| 测试全绿通过，但人工复核发现遗漏了关键异常场景 | 在独立的文件中补充扩展测试或独立行为检查，严禁削弱原有用例 |
| 大模型在对话框中宣称“代码已为您全部修复” | 在受控流水线中跑通全量验证后，再决定是否采纳其补丁 |

### 进入部署发布阶段前的前置核对清单

- [ ] 能在审计记录中清晰追溯基线回归测试、受控 Red 以及最终 Green 的对应运行日志。
- [ ] 已批准的测试用例确实在真实运行时中执行到了核心业务断言。
- [ ] 没有任何为了换取流水线变绿而擅自放宽、删减测试或削弱文档约束的违规行为。
- [ ] 所有故障均经过专业归因分类，且审计记录完整留存。
- [ ] PR 最新的提交（Head Commit）已顺利通过所有必需的自动化检查与人工同行审查。
- [ ] 当前阶段尚未覆盖的剩余技术边界与潜在风险已逐项清晰列出。
