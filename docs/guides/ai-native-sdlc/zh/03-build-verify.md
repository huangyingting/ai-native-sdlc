# 3. 开发与验证：先审查测试，再检验实现

[指南目录](../README.md) · [English](../en/03-build-verify.md) ·
[上一章](02-intent-spec-plan.md) · [下一章：部署与运行](04-deploy-operate.md)

本章继续讲解**当前工单负责人交付**，再结合单独的**历史就绪检查案例**，
说明两个问题：测试怎样才能有效约束实现？测试本身出错时，又该如何处理？

## 3.1 先明确测试阶段与实现阶段的分工

Plan 完整批准后，系统以已批准的文档提交为起点创建工程分支，先分配测试任务，
暂不分配实现任务。Tests PR 合并到本次交付的生命周期分支；随后创建的
Implementation PR 则包含完整变更，目标分支为 `main`。

[![测试审查指出被预期失败遮住的断言问题](https://raw.githubusercontent.com/huangyingting/ai-native-sdlc-demo/main/docs/cases/assets/ownership/tests-request-changes.png)](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8#pullrequestreview-5486915007)

**测试审查，**[huangyingting/ai-native-sdlc-demo#8](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8)。
截图日期：2026 年 10 月 12 日。先确认目标分支、所属阶段和修改范围，再打开
**Files changed**、**Checks** 和
[第二轮修改要求](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8#pullrequestreview-5486915007)。

| Tests 阶段可以做 | Tests 阶段不能做 |
|---|---|
| 增加有意义的验收断言 | 实现生产功能 |
| 运行测试并记录预期失败 | 未执行就填写失败列表 |
| 批准前修正薄弱测试 | 为方便测试而修改已批准 Spec／Plan |
| 保留原有回归测试 | 将导入错误、跳过测试或测试钩子（hook）故障算作有效 Red |

## 3.2 测试是红的，验证任务却可以是绿的

Red 不是“只要测试失败就行”。本仓库要求的受控 Red 必须同时满足：

1. 未修改的基线测试通过。
2. 功能测试确实执行到了预期位置。
3. 失败原因是指定功能尚未实现，测试名称及失败范围与记录一致。
4. 编译、lint 和 build 正常，没有夹杂无关错误。

`tdd-red` 检查的是上述条件。因此，**功能测试应当按预期失败，
`stage-validation` 则应当通过**。两者验证的不是同一件事：前者检查功能行为，
后者检查这次失败是否符合测试阶段的要求。不能以“本来就应该是红的”为由，
忽略阶段校验任务的失败。

本次交付的[最终 Red 检查](https://github.com/huangyingting/ai-native-sdlc-demo/actions/runs/38210170335/attempts/2)
先确认原有 26 项测试通过，再检查测试提交中的 38 项测试：
**29 项通过，9 项为精确匹配的预期断言失败**，没有跳过或基础设施错误。
测试批准对应 `104be0889c54652bec8f9bc317ffa5f0cf33166f`。

## 3.3 不只看有没有测试，还要看断言是否有效

工单归属案例中，首次生成的测试没有直接获批。原因在于，测试看起来覆盖了功能，
并不意味着它足以识别错误实现：

| 不充分的替代指标 | 更有力的实际观察 |
|---|---|
| 下拉选项里有负责人名字 | 正确队列行、详情元数据中真正显示负责人 |
| 时间戳没有变 | 用独立 SQLite 连接观察 `PRAGMA data_version`，确认没有写入 |
| 更新接口返回成功 | 分配、更换负责人和清空的结果，在数据库关闭后重开时仍然保留 |
| 某处能返回所有记录 | 组合筛选的精确集合与空集都正确 |
| HTML 中有 selected 选项 | 挂载控件后执行页面导航，检查选项是否正确同步 |
| 某字段可以更新 | 只有允许字段改变，无关行／字段不变 |

审查时可以反复问：**即使实现错了，这个断言有没有可能仍然通过？**
如果答案是“有”，就应加强测试，或写清它尚未覆盖的部分。
增加测试数量，不一定能增加发现问题的能力。

这次审查经历了两轮修改。第一轮修正了失败名称、历史数据库样本和覆盖不足；
第二轮在 Red 检查已经通过后，仍发现筛选预期违反状态条件、交接后时间戳断言矛盾、
从错误的 DOM 范围查找元素，以及未推进时间的无效重复保存检查。
原因是更早的预期失败遮住了后续断言。**CI 通过与测试本身合理，是两件事。**

## 3.4 实现必须接受已批准测试的检验

Tests PR 审查并合并后，AI 才开始提交实现。审查重点包括：

- 迁移、输入校验和功能行为是否符合 Spec。
- 界面与数据操作是否接通，是否存在写了却没有被调用的辅助函数。
- 已批准的测试、文档和失败清单是否逐字节保持不变。
- 需要补充回归测试时，是否另建文件，而非改动冻结文件。
- 检查与批准是否针对 PR 的当前提交（head），而非此前的提交。

[工单负责人实现](https://github.com/huangyingting/ai-native-sdlc-demo/pull/9)
通过 Stage Green 和应用 CI，包括 **38 项测试、lint、build 和容器冒烟测试**。
此前的 9 项 Red 全部通过，9 个冻结文件未改动。
下文的 50 项来自独立的历史就绪检查案例，不是本次交付的测试数量。

| 必查位置 | 看什么 |
|---|---|
| `stage-validation` | 已批准文件保持不变，此前预期失败的场景全部通过 |
| `validate` | 应用测试、lint 和 build |
| `container-smoke` | 使用生产构建的容器启动并完成冒烟检查 |
| Delivery policy | 当前版本已获得有权限的审查者批准，必需检查及分支规则均满足 |

追加提交后，应按规则重新审查。负责调度的工作流运行成功，也不代表它调度的
应用检查全部成功。

## 3.5 测试本身有缺陷时，不能靠修改产品来迁就

下面转到已归档的就绪检查案例。它采用开发测试模式，不是当前演示的后续交付；
其经验说明，仅验证 Red 仍可能漏掉测试工具的问题：

```text
readiness 路由不存在
  → 测试在路由存在性检查处按预期失败
  → Tests 被批准并冻结
  → 路由实现后，后续断言开始执行
  → 测试工具缺陷暴露
  → Green 失败，实现不合并
```

第一次维护实现
[huangyingting/ai-native-sdlc-discovery-demo#14](https://github.com/huangyingting/ai-native-sdlc-discovery-demo/pull/14)
得到 **44 项通过、4 项失败**。之前测试在“路由缺失”处就已失败，
因此没能执行到以下两处有问题的代码：

1. 简写形式的 `beforeEach` 意外返回了 mock 函数，Vitest 将其作为清理函数调用。
2. 用于观察数据库的 SQLite 长连接，在另一个连接变更表结构后仍缓存着迁移前的列信息。

测试审查未能发现这两个缺陷。处理方式不是修改产品代码来迎合测试，
也不是直接改掉已冻结的测试，而是取消
[huangyingting/ai-native-sdlc-discovery-demo#8](https://github.com/huangyingting/ai-native-sdlc-discovery-demo/issues/8)，
另建 [就绪检查后续任务](https://github.com/huangyingting/ai-native-sdlc-discovery-demo/issues/17)，
说明原因并重新审查。

后续任务在冻结测试之前，先做了一次**隔离的测试工具验证**：将修正后的测试
与尚未合并的路由实现组合运行，48 项全部通过，确认后续断言能够执行。
这是对测试工具（test harness）的验证，不是阶段 Green，也没有将产品代码
放入 Tests 分支。

实现审查又发现了一个问题：代码通过修改异常对象的属性来清理错误信息，
但遇到冻结的异常对象时，这个操作本身会抛错。另加的两项测试复现了问题；
删除这段修改后，**50 项测试全部通过**，所有已批准的测试也保持不变。

这个案例的价值不在于一次成功，而在于发现问题后仍能按规则修正，并保留处理过程。

## 3.6 故意制造错误，检验测试能否发现

可靠性专题进一步检查：这些 readiness 测试究竟能识别哪些错误？
方法是逐个注入有针对性的代码变异，再看测试是否能够检出。

| 注入的错误 | 为什么必须检出 |
|---|---|
| 省略数据库读取 | 看似健康的端点可能根本没检查依赖 |
| 数据库失败仍返回 200 | 不可用实例可能被允许接收流量 |
| 成功或失败时省略 `no-store` | 缓存结果可能掩盖当前状态 |
| 记录原始异常 | 诊断信息可能暴露敏感细节 |
| 修改捕获到的冻结异常 | 错误处理代码本身会再次抛错 |

运行结果是：**13 项原测试通过 → 六个指定变异全部被检出 →
还原代码后 13 项再次通过**。整个过程中，测试文件没有改动。
其中，冻结异常变异触发的是指定测试体内预先允许的应用 `TypeError`，
并非普通断言失败；导入失败、测试钩子错误和超时则不算有效检出。

这说明测试能识别这六种错误，**并不等于测得了整个项目的变异测试分数**。
详细结果见[测试有效性验证记录](https://github.com/huangyingting/ai-native-sdlc-demo/blob/main/docs/archive/brownfield-reliability-rehearsal.md#2-trustworthy-verification)。

## 3.7 失败分类与下一步

| 观察 | 正确处理 |
|---|---|
| 尚未执行功能断言，依赖或导入就失败 | 修复环境或测试工具，不计为有效 Red |
| 代码违反已批准行为 | 在同一契约内修代码，重新检查 |
| 批准前发现测试不足 | 完善测试，重新执行 Red 验证 |
| 冻结的契约或测试工具有错 | 另建任务说明修正范围，保留失败记录 |
| Green 通过，却遗漏了重要异常场景 | 增加独立检查或补充测试，不削弱原测试 |
| 只有模型总结说“修好了” | 执行验证后再决定是否接受 |

### 进入部署前的检查

- [ ] 能分别查到基线、Red 和 Green 的运行结果。
- [ ] 已批准的测试确实执行到了关键断言。
- [ ] 没有为了让检查通过而弱化测试或文档要求。
- [ ] 失败已分类，并保留了对应记录。
- [ ] PR 当前提交已通过所需审查和检查。
- [ ] 尚未验证的行为已明确列出。
