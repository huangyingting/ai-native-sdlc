# 2. 从需求意图到规格与计划：编码前先把问题说透

[指南目录](../README.md) · [English](../en/02-intent-spec-plan.md) ·
[上一章：流程总览](01-operating-model.md) · [下一章：开发与验证](03-build-verify.md)

本章围绕 **“工单负责人”交付主线** 展开：先深入剖析为何需要建立责任人机制，再确立指派与多维筛选规则，最终将这些业务不变量严密拆解为具体的工程实施任务。需求意图（Intent）阐明业务痛点与目标，规格说明（Spec）界定系统行为与可测试的验收条件，而实施计划（Plan）则负责明确如何在现有系统中安全落地并提供验证手段。

## 2.1 聚焦业务痛点，切勿急于敲定实现细节

[![详情页交接规则的产品决定](https://raw.githubusercontent.com/huangyingting/ai-native-sdlc-demo/main/docs/cases/assets/ownership/product-decision.png)](https://github.com/huangyingting/ai-native-sdlc-demo/issues/1#issuecomment-6117980837)

**架构决策实录（2026 年 10 月 12 日）**：建议从
[huangyingting/ai-native-sdlc-demo#1](https://github.com/huangyingting/ai-native-sdlc-demo/issues/1)
的原始需求读起，深入理解为何最终决定将交接入口收敛在工单详情页。

在初始系统中，IT 服务台支持创建、查询与更新工单状态，但始终无法看出每张工单究竟由谁跟进负责。如果需求描述草率地写成“在前端加一个负责人下拉框”，就直接跳过了一系列更为根本的业务与架构问题：负责人字段究竟意味着什么？一线人员应如何指派、转交工单？历史存量数据如何处理？

一份高质量的 Intent 应当结构化包含以下要素：

| 核心维度 | 工单责任归属示例 |
|---|---|
| **业务痛点与依据** | 在模拟交接场景中，责任人归属不透明，亦无法检索未分配工单；应用底层尚无 `owner` 数据模型。 |
| **预期交付成果** | 责任人清晰可见、流转交接具备确定性，同时既有工单流程完全向下兼容。 |
| **目标用户群体** | 一线 IT 支持工程师与服务台团队主管。 |
| **硬性技术约束** | 完整保留存量数据记录与历史时间戳；前端控件必须具备 Accessible 标签并支持键盘导航；分配结果能可靠落盘持久化。 |
| **明确的非目标 (Out of Scope)** | 暂不对接外部 LDAP/SSO 身份目录、暂不引入复杂 SLA 策略、暂不增加邮件通知与批量分配。 |
| **待明确的不确定项 (Unknowns)** | 负责人字段是否必填？候选名单从何而来？仅需界面展示还是需要支持组合筛选？ |
| **如何验证验收** | 校验交互行为、检索结果集合的严密交集，以及数据库重启前后的数据持久化一致性。 |

本功能案例属于合成演练工程，不提供真实的外部用户调研问卷或量化 ROI 估算。在真实的生产交付中，团队应主动补充调研与度量数据；对于尚未明确的信息，应如实列为待调研事项，杜绝在需求初期臆造虚假的技术指标。

## 2.2 借助 AI 精准挖掘规则盲区

交付流程由业务人员提交 Intent 正式拉开序幕：工作流将任务下发给 Documents 自动化流水线，只读权限下的 Copilot CLI 负责深入研读需求并起草第一版规格说明（Spec），经自动化格式检查后，将完整渲染的文档发布至主 Issue 讨论区。
**这一阶段聚焦于需求梳理与规格敲定，严禁触碰任何生产代码、严禁提前创建 Tests PR，亦不触发应用打包。**

在本次真实交付中，团队通过多轮人机交互确立了 4 项核心产品规则：

| 决策编号 | 为什么该决策至关重要 | 最终确认并留痕的结论 |
|---|---|---|
| **Q-1：负责人字段是否必填** | 决定工单创建链路与存量数据的迁移逻辑 | 允许为空（可选）；存量历史工单与新建工单均默认进入“未分配”状态。 |
| **Q-2：候选成员名单从何而来** | 决定参数校验范围、持久化格式与业务边界 | 采用固定的 Alex Chen 与 Sam Rivera 名单；未分配对应存为 `null`。 |
| **Q-3：仅展示还是需要组合筛选** | 决定底层检索 SQL、查询规则与前端路由同步 | 采用交集（AND）逻辑与其他条件组合筛选；页面导航与后退时选项必须正确同步。 |
| **Q-4：在何处交接？有无状态限制** | 决定操作入口与工单状态机是否存在耦合 | 仅在详情页操作，全部 4 种状态下均可流转；建单流程不变，状态与责任人分别独立持久化。 |

每当在 Issue 中答复并确认一项决策，自动化流程便会驱动 Spec 进行一次版本迭代。本次交付最终获批的是 **Spec v5**，随后据此生成并批准了 **Plan v1**。版本号忠实反映了实际的人机迭代轮次，流程本身并未强制要求必须走到 v5。

读者可查阅[4 项决策及各次修订记录](https://github.com/huangyingting/ai-native-sdlc-demo/blob/main/docs/cases/README.md)核对细节。审查的重心在于确认决策结论是否已被严谨地写入验收场景（Acceptance Scenarios），切勿将 AI 随手提出的设计提议误当成人类已经拍板的业务决定。

## 2.3 审查者标准操作规程

在个人演练时，请在专属的隔离仓库中操作，并以该次演练的主 Issue 讨论区为准。以下 `/sdlc` 均为本仓库通过 GitHub Actions 实现的自定义命令，并非 GitHub 官方或 `@copilot` 的原生指令。

1. 仔细通读当前版本的完整 Spec，重点研读需求澄清摘要（Discovery Brief）。
2. 对照业务目标与仓库代码现状，逐项审视 AI 列出的待决问题。
3. 授权审查者在 Issue 中另起一条顶级评论，正式答复特定问题：

   ```text
   /sdlc decide spec v1 Q-1
   Outcome: Tickets may remain unassigned until triage.
   Rationale: Requests arrive before a responsible agent is known.
   ```

4. 等待自动化流水线推送修订版 Spec，确认该项决策已精准固化在验收场景中，再依次回溯下一问题。
5. 若某些非核心问题需延期处理，须按照 [defer 指令规范](../../../../tools/brownfield-demo/README.md#spec-readiness-profiles)
   详细登记延期缘由、跟进责任人、后续任务与技术风险。延期挂起绝不等于问题已被解决。
6. 若 Spec 内容存在偏差，可提交 `/sdlc revise spec` 附带具体修订意见。
7. 当所有阻塞性问题均妥善解决后，明确签署批准当前版本：

   ```text
   /sdlc approve spec v5
   ```

注：命令中的 `v1`、`Q-1`、`v5` 均为示例编号，演练时请替换为主 Issue 中实际出现的版本号。指令必须置于新评论的首行，严禁包裹在 Markdown 代码块（\`\`\`）内，亦不可通过编辑旧评论来发送指令。普通的日常交流与单纯 `@copilot` 不会被系统识别为审批动作。

## 2.4 将 Spec 转化为具备高可测试性的行为契约

[![Spec v5 的批准与回执](https://raw.githubusercontent.com/huangyingting/ai-native-sdlc-demo/main/docs/cases/assets/ownership/spec-approved.png)](https://github.com/huangyingting/ai-native-sdlc-demo/blob/9e183465d985bfa081f239a68eda400340320195/docs/delivery-runs/brownfield-human-gated-delivery/1/spec.md)

**Spec v5 获批留痕**：上方截图展示了审批指令与系统处理回执，点击可溯源至固定提交中的完整规格文档。

一份严密的 Spec 必须讲透系统行为与预期结果，但无需过早绑死具体代码实现。例如，获批规格中关于工单分配的验收场景概括如下：

```text
前置条件：工单 INC-0001 当前处于未分配状态。
用户操作：用户在工单详情页从候选名单中选中 Alex Chen 并点击保存。
预期结果：详情页与工单列表均正确展示该负责人；
         强刷浏览器页面，或在持久化存储上重启应用后，分配结果依然保留；
         该工单的历史时间戳与其他字段完好无损。
```

除正常主流程外，Spec 必须巨细靡遗地覆盖边界异常与向后兼容场景：

- **清空负责人**：底层数据库显式持久化为 `null`，前端界面统一呈现为 `Unassigned`。
- **重复提交相同值**：底层数据库严禁产生不必要的重复写入（需通过 SQLite 数据版本检测验证，不能单纯依赖时间戳未变）。
- **非法输入防御**：提交名单外的非法成员或操作不存在的工单，服务端显式抛出错误且数据库严禁产生脏写入。
- **多维组合筛选**：负责人、关键词搜索、状态与优先级之间必须按 **AND** 逻辑取交集，严禁错写为 OR。
- **单项筛选重置**：重置负责人条件时，其余维度的筛选条件必须妥善保留，浏览器前进/后退时控件状态能正确同步。
- **数据迁移兼容**：在升级包含老数据的数据库时，系统自动追加允许为空的 `owner` 列，历史存量工单数据完整无缺。

诸如“筛选功能正常”这类模糊描述在 Spec 中是绝不合格的，必须明确断言返回的工单集合。在本次实际镜像验证中，设置 `Sam Rivera` + `Open` + `High` + `inc-1` 仅精准返回 INC-0001 一张工单；切换为 `Alex Chen` 则返回空集合。这些断言严重依赖测试数据集的准备，切不可直接套用在刚初始化的空库上。

## 2.5 实施计划（Plan）必须扎根于真实代码事实

[![Plan v1 的独立批准](https://raw.githubusercontent.com/huangyingting/ai-native-sdlc-demo/main/docs/cases/assets/ownership/plan-approved.png)](https://github.com/huangyingting/ai-native-sdlc-demo/blob/6b7a4ddf96f43c6f1980c2e1ed4b568ec429d427/docs/delivery-runs/brownfield-human-gated-delivery/1/plan.md)

**Plan v1 独立获批留痕**：点击可查阅计划全文，核对验收场景、实施任务与验证策略的严密映射。计划中规划的验证手段属于实施设计，绝不能直接等同于已经跑通的测试结果。

Plan 的核心职责是阐明如何在现有系统中安全兑现 Spec。审查计划时，必须严格核验任务依赖链、改动文件边界与验证策略，切不可只粗略看一眼任务标题。

| 规划任务示例 | 前置依赖 | 验证手段与断言策略 |
|---|---|---|
| **数据库表结构扩展与兼容迁移** | 已获批的分配规则 | 校验迁移前历史数据行与已有字段值 100% 保持未变 |
| **实现流转 API 并防范重复写入** | 存储层接口规范 | 覆盖非法输入、幂等重复保存与数据库重启恢复测试 |
| **在列表与详情页渲染展示负责人** | 存储层查询输出 | 断言页面真实渲染出指定成员文本，而非仅检查下拉框选项 |
| **实现交集筛选并同步前端路由** | 检索规则设计 | 断言多维组合筛选的精确集合、单项重置与浏览器历史流转 |
| **全量回归创建、状态流转与检索** | 完整工程变更 | 跑通已冻结的既有回归测试用例与容器端到端冒烟测试 |

计划中对仓库技术能力的每一处假设，均必须能在现有工程源码或工具集中找到确凿证据。

一旦在计划中发现任务遗漏或技术假设偏差，审查者应使用 `/sdlc revise plan` 提交修订意见。经修正复核无误后，再行签署正式批准：

```text
/sdlc approve plan v1
```

## 2.6 契约冻结与阶段保护机制

在实施计划（Plan）获得正式批准前，对规格说明（Spec）的主动修订会导致原 Spec 审批及关联的 Plan 即刻自动失效。
而一旦实施计划获得正式审批，流水线会立即**冻结 Spec、Plan 及全部审批上下文**，并**仅向下游下发测试用例编写任务（TDD Tests）**。此后若因业务变化需要调整功能范围，必须另行发起新的需求意图（Intent），严禁直接在后续代码实现中私自追加要求。

当前演示案例完整展现了产品决策如何驱动规格持续迭代。之所以未演示“撤销已获批的 Spec”，是因为 v1 至 v4 属于探索过程中的中间版本，本来就未曾获批。若需专门检验“撤销已批准 Spec 导致关联 Plan 连锁失效”的安全机制，可单独演练“显式 Spec 修订（ownership-spec-revision）”场景。

### 进入编码开发阶段前的前置核对清单

- [ ] 业务痛点描述有据可查，关键未知项与待决问题已明确列出。
- [ ] 所有阻塞性问题均已通过决策解决，延期项已完整登记延期理由、责任人与技术风险。
- [ ] 验收场景全面覆盖了边界异常、向后兼容与幂等性要求，绝非仅关注正向 Happy Path。
- [ ] Plan 中对系统能力的各项工程假设均能在代码库中找到对应实现支撑。
- [ ] 任务分解与 Spec 中的验收场景具备清晰的双向映射，且任务依赖拓扑无循环死锁。
- [ ] 审查团队充分理解并确认：一旦批准 Plan，所有上游文档与契约即刻冻结，不可随意篡改。
