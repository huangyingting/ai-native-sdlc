# 规格驱动开发（SDD）基准评测用例指南

[English](sdd-benchmark-use-cases.en.md)

本指南提供跨技术栈、零外部依赖的标准基准用例，专门用于横向评测各类**规格驱动开发（Spec-Driven Development, SDD）**框架与工作流（例如 GitHub Spec Kit、Kiro、BMAD、OpenSpec 或自定义“先规格后实现”流水线）。

关于更完整的早期需求阶段研究，以及本仓库自身的人工门禁规格审查流程，请参阅[需求意图澄清、规格说明与计划编制的深入研究](../research/ai-native-sdlc-early-stage-research.md)与[AI 原生软件交付系统指南](ai-native-sdlc/README.md)。

<a id="1-what-makes-a-good-sdd-benchmark-use-case"></a>
## 1. 优秀的 SDD 评测用例应具备哪些特征

过于简单的 CRUD 题目无法区分不同 SDD 框架的优劣，因为大模型无需编写规格说明也能一次性生成代码；而过于庞大的企业级系统又会导致跨工具对比的评测成本过高。一个真正有效的 SDD 基准用例必须同时满足以下四个条件：

| 特征 | 对 SDD 评测的意义 |
|---|---|
| **业务概念直观** | 无需特定行业背景，任何工程师都能在 30 秒内理解业务目标 |
| **跨语言且零外部依赖** | 可在任意编程语言中以纯逻辑库、CLI 或轻量 REST API 形式实现 |
| **包含蓄意的规格歧义点** | 检验框架的 **Specify / Clarify（规格/澄清）** 阶段能否主动识别并追问未决业务规则，而非静默脑补假设 |
| **包含非平凡的工程不变量** | 检验 **Plan / Task / Implement（计划/任务/实现）** 阶段能否在架构与测试中化解棘手边界，而非只写理想路径代码 |

<a id="2-use-case-1-order-discount-and-partial-refund-calculator"></a>
## 2. 用例一：订单多券折扣与分批部分退款计算器（金额分摊与组合规则）

本用例重点考察 SDD 框架对**多规则组合优先级、跨批次有状态操作以及精确金额分摊计算**的处理能力。

### 2.1 初始提示词（可直接复制用于测试）

向被测 SDD 框架输入以下完全一致的初始需求描述：

```text
Build an Order Checkout and Refund service. Users can create an order with multiple line items (quantity and unit price) and apply promo codes. Support three promo types: percentage off the order, fixed amount off the order (with a minimum spend threshold), and buy-X-get-Y-free on a specific item. After checkout, users can request a refund for one or more items (partial or full return) across multiple separate return requests, and the system must calculate the exact refund amount for each request.
```

> **中文对照参考（如使用中文评测）：**
> 构建一个订单结账与退款服务。用户可以创建包含多个商品行（数量与单价）的订单并使用优惠码。支持三种优惠类型：整单百分比折扣、带最低消费门槛的整单固定金额立减，以及指定商品的“买 X 送 Y”。结账后，用户可以通过多次独立的退货请求，申请退回一个或多个商品（部分退款或全额退款），系统必须精确计算每次请求应退还的金额。

### 2.2 需求澄清陷阱（考察 Specify / Clarify 阶段）

薄弱的 SDD 工作流会直接自行假设规则并开始生成代码；优秀的 SDD 工作流会在锁定规格前，主动暂停并追问以下 **4 个未明确的核心业务决策**：

1. **多优惠码叠加规则与计算先后顺序**
   - 同一笔订单是否允许叠加多个优惠码？
   - 若允许叠加，按什么顺序依次生效？
   - *为何关键：* 对一笔 `$100.00` 的订单，先减 `$20.00` 再打 `9 折` 实付 `$72.00`；先打 `9 折` 再减 `$20.00` 则实付 `$70.00`。
2. **部分退款导致跌破满减门槛时的处理策略（按比例分摊 vs. 优惠收回/倒扣）**
   - 假设用户购买 `$100.00` 商品，使用“满 `$100.00` 减 `$25.00`”优惠券（实付 `$75.00`），随后退掉一件原价 `$30.00` 的商品，保留商品原价总额变为 `$70.00`（低于 `$100.00` 门槛）。
   - 此时应按实付比例退还 `$22.50`（**按比例分摊**），还是因不满足满减门槛而收回 `$25.00` 优惠、仅退还 `$30.00 - $25.00 = $5.00`（**门槛收回/倒扣**）？
3. **“买 X 送 Y”商品发生部分退货时的计价规则**
   - 当用户“买 2 送 1”（以 2 件的价格获得 3 件同款商品）后申请退货 1 件时，该次退款是退 `$0.00`（优先视作退回赠品）、退原价，还是按每件 $\frac{2}{3}$ 的均摊实付价退款？
4. **折扣下限与边界范围**
   - 固定金额立减是否会将订单或商品行金额减至 `$0.00` 以下？税费与运费是否在本次范围之外？

### 2.3 预设标准澄清答复（用于统一跨框架基线）

当被测 SDD 工具发起澄清提问时，统一提供以下答复，以确保不同框架在相同业务规则下进入后续阶段：

- **叠加与顺序：** 允许叠加多张优惠码。按“单品级优惠（买 X 送 Y）→ 整单固定金额满减 → 整单百分比折扣”的顺序依次计算。
- **满减部分退款策略：** 采用**按实付比例分摊（Pro-rata allocation）**，不执行优惠倒扣收回（避免小额退货出现 `$0.00` 或负数退款）。
- **买 X 送 Y 部分退款策略：** 将每组 $(X + Y)$ 件商品的总实付金额均匀分摊到该组内的每一件商品上。
- **金额下限与范围：** 订单与商品单元应付金额最低为 `$0.00`（不出现负数）；税费与运费不在范围内。

### 2.4 高难度工程实现点（考察 Plan & Code 阶段）

即使上述业务规则全部澄清完毕，该用例依然隐藏着一个经典的工程实现陷阱：**分批退款中的“一分钱拆解 / 累计舍入误差”漏洞（Penny-Splitting Bug）**。

#### 为什么朴素实现一定会出错

假设用户购买了 **3 件单价 `$10.00` 的商品**（原价合计 `$30.00`），使用了一张 **整单立减 `$10.00`** 的优惠券，订单总实付为 **`$20.00`**。

随后，用户分 **3 次独立的退货请求**，每次退回 1 件商品：

- 每件商品理论分摊的实付金额为 $\$20.00 \div 3 = \$6.6666\dots$
- 如果每次退款请求独立执行四舍五入（`$6.67`），3 次退货累计退款为 `$6.67 × 3 = $20.01`（**多退了 1 美分，造成资金损失**）。
- 如果每次退款直接向下截断（`$6.66`），全部退完后累计退款为 `$6.66 × 3 = $19.98`（**全额退货却少退用户 2 美分**）。

#### 优秀的 SDD 技术计划必须明确的设计要求

1. **使用整数最小货币单位（Integer cents）：** 所有金额必须以整数“分”（cents）存储与计算，严禁直接使用 IEEE 754 浮点数。
2. **结账时分摊到最小退货单元（最大余额法 Largest Remainder Method）或维护可退余额对账：**
   - 在结账锁定订单时，使用最大余额法将整单折扣精确分摊到每一件可退商品单元（例如 3 件商品分别记录实付 `667`、`667`、`666` 分）；**或者**
   - 在订单/商品行状态中持久化维护 `refunded_cents`（已退分）与 `remaining_refundable_cents`（剩余可退分），确保最后一件商品退货时精确收敛到剩余可退余额。

### 2.5 黄金验收测试用例

使用以下 3 组确定性用例检验最终生成的代码与测试套件：

| 用例编号 | 结账初始状态 | 分批退货序列 | 期望退款结果 | 验证的核心不变量 |
|---|---|---|---|---|
| **ORD-1** | 3 × `$10.00`（原价 `$30.00`），整单减 `$10.00`（实付 `$20.00`） | 分 3 次独立请求，每次退 1 件 | 第 1 次：`$6.67`，第 2 次：`$6.67`，第 3 次：`$6.66`（或 `$6.66, $6.67, $6.67`，3 次总和必须严格等于 `$20.00`） | 多次部分退款的累计总额严格等于实付总额，不超退也不少退 |
| **ORD-2** | 商品 A `$60.00` + 商品 B `$40.00`，叠加“满 `$80` 减 `$20`”与“整单 `10% off`”（实付 `$72.00`） | 第 1 次退商品 A；第 2 次重复申请退商品 A | 第 1 次：`$43.20`；第 2 次：拒绝请求（超出已购可退数量） | 多券叠加顺序（`$100 -> $80 -> $72`）+ 退货数量幂等/防超退校验 |

### 2.6 二期演进测试：规格变更与影响分析（`v1 -> v2`）

许多 SDD 工具仅擅长从零生成第一版（`v1`），一旦引入需求变更就会破坏原有规格或代码不变量。在 `v1` 验收通过后，可继续输入以下 `v2` 变更提示词，评测框架的**规格增量演进、变更影响分析与向后兼容能力**：

```text
Extend the Order Checkout and Refund service to support split payment at checkout (Gift Card balance + Credit Card) and a return reason (`defective` vs. `changed_mind`) on refund requests. `changed_mind` returns incur a 10% restocking fee, whereas `defective` returns receive a full prorated refund.
```

> **中文对照参考：**
> 扩展订单结账与退款服务，支持结账时的组合支付（礼品卡余额 + 信用卡），并在退款请求中增加退货原因（`defective` 质量问题 vs. `changed_mind` 无理由退货）。`changed_mind` 退货需扣除 10% 的重新上架费（restocking fee），而 `defective` 退货则退还完整分摊实付金额。

- **`v2` 新增澄清陷阱：**
  1. **组合支付的退款退回顺序（Tender Waterfall）：** 当一笔由礼品卡支付 `$30.00`、信用卡支付 `$50.00` 的订单发生部分退款时，优先退回哪个渠道（优先退信用卡、优先退礼品卡，还是按支付比例原路分摊退回）？
  2. **10% 重新上架费的计算基数：** `10%` 扣费是基于商品的**原价**计算，还是基于折扣后的**分摊实付金额**计算？
- **`v2` 新增高难度工程实现点：**
  - **跨支付渠道与扣费的资金守恒不变量：** 在多次混合原因（部分 `defective`、部分 `changed_mind`）的分批退货中，`累计退回信用卡 + 累计退回礼品卡 + 累计扣留上架费` 绝不能超过订单初始总实付金额，同时必须完全兼容 `v1` 的一分钱拆解不变量（`ORD-1` 至 `ORD-3`）。

<a id="3-use-case-2-smart-meeting-room-booking-service"></a>
## 3. 用例二：智能会议室预订服务（时间序列与状态变更不变量）

如果你希望考察 **时间区间推理、缓冲期重叠计算以及状态更新不变量**，可以使用第二个基准用例。

### 3.1 初始提示词（可直接复制用于测试）

```text
Build a Meeting Room Booking service. Users can book a room for a time range and attendee headcount, modify or cancel bookings, query available rooms for a time window, and create a weekly recurring booking for up to N weeks. Every room requires a 15-minute cleanup buffer between meetings.
```

> **中文对照参考：**
> 构建一个会议室预订服务。用户可以按时间段和参会人数预订会议室、修改或取消预订、查询指定时间段内的可用会议室，以及创建最多连续 N 周的每周周期性预订。每间会议室在两场会议之间必须留出 15 分钟的清洁缓冲时间。

### 3.2 需求澄清陷阱（考察 Specify / Clarify 阶段）

优秀的 SDD 框架应当在规格阶段识别并追问以下 **4 个模糊点**：

1. **周期性预订遇到单次冲突时的处理策略（原子全败 vs. 跳过冲突周 vs. 自动换房）**
   - 当创建一个连续 8 周的周期性预订，若第 3 周与已有会议冲突：是整组 8 周预订全部失败回滚（**All-or-Nothing**），还是成功预订其余 7 周并标记第 3 周跳过（**Best-Effort**），抑或为第 3 周自动分配另一间满足人数的会议室？
2. **15 分钟清洁缓冲区的边界规则**
   - 清洁缓冲区是否受会议室每日开放/关闭时间限制（例如会议室 `18:00` 关闭，最后一场会议能否约到 `18:00`，还是必须 `17:45` 结束）？
   - **同一组织者**在同一会议室连续预订两场背靠背会议时，中间是否仍强制要求 15 分钟清洁缓冲？
3. **周期性预订的取消与修改粒度**
   - 用户取消或改期时，是仅支持整组系列取消，还是支持“仅本次日程（this occurrence）”与“本次及后续日程（this and following）”？
4. **会议室分配方式**
   - 调用方是显式指定 `roomId`，还是由系统按参会人数自动分配容量最小且够用的会议室（Best-Fit 最佳匹配）？

### 3.3 高难度工程实现点（考察 Plan & Code 阶段）

1. **原地修改预订时间时的“自身冲突排除（Self-Overlap Exclusion）”**
   - 当用户将自己已有的 `10:00–11:00` 预订修改为 `10:30–11:30` 时，朴素的可用性检查会查询该会议室在 `10:30–11:30`（含前后 15 分钟缓冲）内是否存在有效预订——结果与该预订**修改前自身的 `10:00–11:00` 记录**发生重叠，导致合法的时间微调被错误拒绝。
2. **跨夏令时（DST）切换的本地挂钟时间周期推算**
   - 在支持时区的场景下，每周二 `09:00–10:00 America/New_York` 的周期性会议跨越夏令时切换日时，必须保持本地挂钟时间 `09:00` 不变。若代码简单使用 UTC 毫秒数累加（`start_utc + 7 * 86400_000`），跨越夏令时后会议时间会偏移为 `08:00` 或 `10:00`。

### 3.4 黄金验收测试用例

| 用例编号 | 测试场景 | 期望结果 | 验证的核心不变量 |
|---|---|---|---|
| **RM-1** | 预订 A 为 `10:00–11:00`，用户在同会议室申请预订 B `11:10–12:00` | 拒绝请求；最早可预订开始时间为 `11:15` | 15 分钟清洁缓冲时间强制生效 |
| **RM-2** | 预订 A 为 `10:00–11:00`（同房间另有预订 C `12:00–13:00`），用户将预订 A 原地调整为 `10:15–11:45` | 修改成功（`11:45 + 15 分钟缓冲 == 12:00`，且预订 A 不会与修改前的自己冲突） | 原地更新排除自身记录 + 缓冲区半开区间边界（`end + buffer == next.start` 合法） |
| **RM-3** | 创建连续 4 周的周期性预订，其中第 3 周存在时间冲突 | 严格遵循已澄清的原子/跳过策略，并明确返回第 3 周的冲突详情 | 周期性冲突行为与规格说明完全一致 |

### 3.5 二期演进测试：规格变更与影响分析（`v1 -> v2`）

在 `v1` 验收通过后，输入以下 `v2` 变更需求，考察 SDD 框架如何增量修订规格并演进既有数据模型：

```text
Update the Meeting Room Booking service so that meetings with more than 10 attendees require a 30-minute cleanup buffer instead of 15 minutes, and allow users to reschedule or change the headcount of a single occurrence within a recurring series without cancelling the rest of the series.
```

> **中文对照参考：**
> 更新会议室预订服务：参会人数超过 10 人的会议需要 30 分钟清洁缓冲时间（而非 15 分钟）；同时允许用户单独改期或修改周期性预订中的某一次日程（含修改人数），而不取消该系列中的其余日程。

- **`v2` 新增澄清陷阱：**
  1. **非对称缓冲区方向：** 清洁发生在会议结束之后。若前一场会议 A 为 6 人（需 `15` 分钟缓冲），后一场会议 B 为 12 人（需 `30` 分钟缓冲），A 与 B 之间只需间隔 `15` 分钟（按前序会议清洁时长），还是取 `max(15, 30) = 30` 分钟？
  2. **修改人数导致缓冲区膨胀冲突：** 当用户将已有预订的参会人数从 `8` 人改为 `12` 人，其会后缓冲从 `15` 分钟扩大到 `30` 分钟并与下一场会议冲突时，系统是拒绝修改人数，还是自动尝试换房？
  3. **单次日程改期后的整组取消行为：** 若周期性预订的第 2 周日程被单独改期（成为例外实例），随后用户取消整个周期系列，该被改期的第 2 周日程是否一并取消？
- **`v2` 新增高难度工程实现点：**
  - **周期系列的单次例外状态关联（Linked Recurrence Exceptions）：** 修改单次日程时既要脱离原时间槽，又要保留与父系列的关联（`seriesId` + `occurrenceIndex`），防止后续查询或整组变更时产生孤儿日程或已取消日程复活。

## 4. SDD 框架横向评测评分表

使用同一基准用例测试不同 SDD 工具时，可按以下五个阶段维度进行量化打分：

| 评测阶段 | 评估维度 | 0 分（薄弱） | 1 分（部分达标） | 2 分（优秀） |
|---|---|---|---|---|
| **1. 意图与澄清（Specify & Clarify）** | **歧义识别能力** | 静默脑补业务规则，直接生成规格或代码 | 仅追问表层格式问题（如字段名），遗漏核心业务陷阱 | 在锁定规格前，精准识别并追问核心规则歧义（如叠加顺序、跌破满减门槛、周期冲突策略） |
| **2. 规格编写（Specification）** | **验收标准具体性** | 仅有含糊描述（如“准确计算退款金额”） | 用文字定义了规则，但缺少带精确数字/时间的边界算例 | 包含 Given/When/Then 验收场景，并给出精确到美分或分钟的边界算例 |
| **3. 技术计划（Plan）** | **不变量与边界设计** | 只有通用目录结构或框架套话 | 提到需要注意舍入或时间冲突，但未给出确定性算法 | 明确设计不变量方案（如整数分 + 最大余额法/剩余可退余额收敛，或更新时排除自身 ID） |
| **4. 任务与实现（Tasks & Code）** | **测试追溯与一次通过率** | 测试仅覆盖理想路径，黄金边界用例失败 | 需要人工二次提示修复后才通过黄金用例 | 生成的任务拆解与自动化测试直接覆盖全部黄金边界用例，且首次运行全部通过 |
| **5. 规格演进（`v1 -> v2`）** | **变更影响与回归安全** | 推翻重写 `v1` 规格/代码，或破坏 `v1` 黄金测试用例 | 机械追加 `v2` 功能，但忽略与 `v1` 不变量的交叉影响 | 清晰增量更新规格文档，主动追问 `v1 × v2` 交叉边界，且同时通过 `v1` 与 `v2` 全部测试 |
